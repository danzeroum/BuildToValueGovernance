# Fail-Secure First

BuildToValue **fails closed by default**. When the gateway cannot produce a
valid evidence or detects a policy violation, it responds with
`HTTP 451 Unavailable For Legal Reasons` — **not** with `500`, **not** with a
silently degraded happy path.

This is the system's most important security invariant. Everything you will
learn in the Portal is oriented around it:

- The [first tutorial](../tutorials/01-handle-failure.md) teaches the block,
  not the happy path.
- The reference documentation is [generated by a fail-secure script](https://github.com/danzeroum/BuildToValueGovernance/blob/main/scripts/autogen_reference.py)
  that aborts the build if any expected invariant is missing.
- The playground presents the block as **educational experience** — not as a
  frustrating error (see [contestability](contestability-loop.md)).

## Why this matters

In traditional systems, "fail open" is the temptation: keep the service alive
at all costs. In BTV, the product **is** auditable trust. A success without
valid evidence equals a failure — and a failure without a contestation trail
is a betrayal of the end user.

## The practical rule

If you write code that catches a BTV exception and silently returns `200 OK`,
you have broken the contract. Always propagate the `451`, always display the
[contestation trail](contestability-loop.md), always let the end user appeal.
