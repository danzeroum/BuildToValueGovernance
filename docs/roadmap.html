Diagnóstico Validado

O que o código confirma

Validação independente contra o repositório real, auditando estrutura de diretórios, testes compile-fail e arquitetura do núcleo híbrido.

Pilar 1 — Moat Criptográfico
✓ Confirmado — subestimado
10+ testes compile-fail cobrem toda a cadeia: EvidenceToken, EscalatedVerdict, DeliveryToken, InclusionReceipt. Bypass estruturalmente impossível.
Pilar 2 — Gateway Axum
⚠ Parcial — mal diagnosticado
Callbacks nos SDKs são uma decisão arquitetural, não falha. O problema real: o Gateway recebe decisões para validar, não intercepta tráfego de rede proativamente. PROP-029 confirma a lacuna.
Pilar 3 — Contestability Loop
⚠ Confirmado — dualidade não reconciliada
Lógica de contestação existe em rust/gateway/routes/appeals.rs E em python/governance/contestability_loop.py. Migração em curso, não documentada como tal.
Pilar 4 — Policy-as-Code
✓ Confirmado — amplitude real
Motor inclui safe_expression_evaluator.py (14KB), sector_loader.py, profile_manager.py. Riqueza é ativo de longo prazo, obstáculo para First Success.
Gap Não Diagnosticado
✗ Ausência de testes E2E
Nenhuma fixture testa o fluxo completo: Agente → SDK → Gateway → Verdict → Ledger → Dashboard. O sistema que vende garantias criptográficas não prova seu caminho crítico automaticamente.
Posicionamento de Mercado
✗ Visão não traduzida
O código fala latência, HMAC e bytes. O comprador (CISO, DPO) fala multas, horas de auditoria e conformidade. Nenhuma métrica de negócio está surfacada como valor primário.
Fase 1 — Semanas 1–3

First Success em < 15 minutos

Encapsular o que existe para que um decisor técnico — não um engenheiro de integração — execute um comando e veja um resultado de negócio em minutos.

⚡
Invariante da Fase 1

Nenhum código de proteção novo. Zero engenharia adicional de segurança. O kernel Rust e o motor de políticas Python estão prontos. O trabalho é exclusivamente de orquestração, empacotamento e UX de onboarding.

Fase 2 — Semanas 4–8

Gargalo de Validação Inescapável

Transformar o BTV de uma biblioteca que exige cooperação do desenvolvedor em infraestrutura de rede que se impõe sem modificação do código do agente.

ALTA PRIORIDADE Ação B1 — Proxy HTTP Transparente (Drop-in) Semanas 4–6
B1.1 — Rota proxy_forward no Axum
Reverse proxy que intercepta e reencaminha
Implementar rota que recebe requisições destinadas a api.openai.com ou bedrock.amazonaws.com, valida contra o motor de políticas, e reencaminha se aprovado. Em caso de bloqueio: HTTP 451 com receipt de evidência no body.
OPENAI_BASE_URL=http://btv-gateway:8080/proxy \
openai.api_key="..." # zero alteração no agente
Esforço Alto ↑ Impacto Crítico
B1.2 — Resolução da PROP-029
Transactional Safety Gate via interceptação HTTP
A PROP-029 fica resolvida para o tráfego HTTP via proxy. O Gateway passa a ser um operador de rede que bloqueia uma ação de negócio real — não apenas um validador que emite vereditos. Moat operacional real, não teórico.
Esforço Alto ↑ Impacto Crítico
B1.3 — Manter SDKs como caminho avançado
B2D via callbacks, B2B via proxy
SDKs (LangChain, CrewAI, AutoGen, LlamaIndex) permanecem para desenvolvedores que querem controle fino sobre o fluxo de evidências. O proxy é o caminho de adoção para compradores de compliance (CISO/DPO) que não controlam o código do agente.
Esforço Baixo ↑ Impacto Alto

ALTA PRIORIDADE Ação B3 — Reconciliar Dualidade Rust/Python (Contestation) Semanas 6–8
B3.1 — Definir fronteiras rígidas
Rust: plano de controle. Python: plano analítico.
Rust (Gateway Axum): validação de invariantes criptográficas, roteamento HTTP, gestão de memória, rotas de appeals como endpoint de ingestão. Python (Governance): motor analítico, chamadas a LLMs, ML models, escalação semântica. FFI deve refletir esta separação.
Esforço Médio ↑ Impacto Médio
B3.2 — Desabilitar contestação no bundle de demo
Contestability como feature de expansão, não pré-requisito
O quickstart não deve abrir um banco de appeals nem exigir que o cliente entenda SLAs de 24 horas. A contestação é um diferencial para expansão. Desabilitar no policy bundle padrão. Documentar claramente o estado de migração Rust/Python no ADR correspondente.

Invariantes Preservados

O que não muda em nenhuma fase

O plano de encapsulamento não toca nos invariantes arquiteturais do kernel. Toda ação das Fases 1–3 opera fora do hot path.

Fail-Secure
BLOCK em qualquer erro. O proxy herda este comportamento — em caso de timeout ou falha do motor, a requisição é negada, nunca aprovada por padrão.
TechnicalEvidence
9632 bytes fixos, BLAKE3. O tamanho canônico e o alinhamento de memória contra side-channels não são negociáveis. Os bundles não alteram a estrutura da evidência.
Zero Heap no Hot Path
O proxy_forward não deve alocar no caminho crítico. Ring buffer e stack allocation preservados. Latência P99 <50ms é requisito, não sugestão.
Affine Types
EvidenceToken, DeliveryToken, InclusionReceipt — todos os tipos com custódia linear. Nenhum bundle ou proxy pode contornar o sistema de ownership do compilador Rust.
HMAC-SHA256
Responsabilidade assinada em toda decisão. O proxy não delega assinatura — o kernel Rust assina cada verdict antes do reencaminhamento.
explain_decision()
Toda decisão exposta ao cliente via proxy deve ter explain_decision() disponível. Transparência radical não é opcional no modelo de negócio do Trust OS.
