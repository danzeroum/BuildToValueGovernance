FROM THE WILD WEB TO THE ZOO: BENCHMARKING
WEB AGENTS WITH A REALISTIC SIMULATOR
Anonymous authors
Paper under double-blind review
ABSTRACT
Web agents are language-based AI systems capable of executing multi-step online workflows. They interact with the web in unexpected ways and present new
classes of security challenges. Ensuring that these interactions are safe requires
rigorous testing. However, the web’s heterogeneity and lack of reproducibility, together with the complexity of language-model-driven agents, complicate rigorous
security evaluation. Robustly evaluating web agents requires an environment that
preserves the complexity they face in the wild while providing a level of reproducibility unavailable online.
We introduce ZOO, a simulated web environment that enables realistic workflows
across multiple interconnected web applications—including email, identity management, e-commerce platforms, collaborative tools, and web analytics—within
a single network. Unlike the open web, it also provides full access to backend
state and supports deterministic re-initialization, both of which are essential for
robust verification of AI systems. Building on top of the ZOO infrastructure, we
then implement a variety of proof-of-concept web agent evaluations designed to
showcase ZOO’s interconnected services and leverage the transparent backend for
capability and security verification.
INTRODUCTION
Web agents are AI systems capable of operating a web browser in response to high-level user
prompts. Although only recently made technically feasible, they are already being deployed across
a range of environments, including web browsers (Microsoft, 2024a; OpenAI, 2025; Perplexity AI,
2025), browser extensions (Claude, 2025), and standalone developer tools (Browser Use, 2024;
Skyvern, 2024; Fireworks AI, 2024). With direct control over user interactions, they pose risks that
challenge existing security assumptions and demand systematic evaluation.
Web agents are capable of multi-step and multi-site workflows, and can dynamically adjust their
planned actions based on observations from web pages. Throughout this process, web agents are routinely exposed to untrusted content and act as more than passive consumers: they can autonomously
navigate to URLs, provide user credentials, and perform arbitrary actions within web pages, such as
clicking buttons and submitting forms. In particular, web agents are highly susceptible to indirect
prompt injection attacks (Evtimov et al., 2025; Witt, 2025), in which attacker-controlled content
causes an agent to misinterpret external text as part of its own instructions, thereby enabling an
attacker to take arbitrary actions on a user’s behalf.
Evaluating the overall behavior and security properties of a web agent requires more than simply
observing task completion on a live website. It requires an environment that closely matches the
open web while providing two capabilities absent from production settings: state observability and
experimental reproducibility.
The open web offers the most authentic attack surface, yet it provides neither of these properties.
Researchers cannot inspect backend state to determine, for example, whether an agent has executed
an unwanted operation. On the open web, each execution reflects a unique moment in time, as data
changes, content is personalized, and site behavior evolves. Additionally, bot-detection mechanisms
such as CAPTCHAs and network intermittency further limit controlled experimentation. Finally,
ethical considerations require ensuring that experiments do not disrupt real users or operational
systems.

Existing benchmarks offer controlled environments but lack the interconnected structure or realworld applications and services needed for security research. Text-based LLM evaluation systems
remove the browser entirely and cannot capture dynamic page behavior or evaluate different agent
architectures (visual input, accessibility tree, DOM, or hybrid approaches). More realistic benchmarks like VisualWebArena (Koh et al., 2024) provide individual self-hostable web applications
with seeded databases and backend state access for evaluation. However, they offer a limited number
of applications—a social forum, e-commerce site, and classifieds board—which share no services
and cannot communicate with each other.
To the best of our knowledge, no existing benchmark provides an email server and webmail client,
despite email being a primary vector for attacks. More broadly, many interconnected applications
and services exist on the modern web—productivity tools, identity providers, web analytics, feed
readers—that are not well represented in existing benchmarks. Building such an environment requires substantial infrastructure engineering that is peripheral to most security research questions.
To compensate, we present ZOO as shared infrastructure to eliminate this barrier. ZOO is a simulated web environment composed of over a dozen interconnected applications. It offers full state
observability, allowing direct inspection of backend databases and services from the host system and
ground-truth verification of agent behavior. It also supports deterministic resets, whereby application
state can be restored to committed snapshots so that experiments begin from identical conditions.
Finally, it provides realistic complexity, integrating (to date) 13 functional web applications within
a shared network to support multi-step, cross-application workflows.
Contributions. In detail, our main contributions are:
(1) Design and Architecture of ZOO: We present the design and architecture of ZOO, a simulated
web environment that enables precise state observation and deterministic control (Section 3).
(2) Scenario Construction API (ZOO’s scenario constructor): Along with the ZOO infrastructure
and site portfolio, we also introduce a framework for constructing realistic evaluations of web agents,
and use it to build a proof-of-concept benchmark featuring a variety of tasks. (Section 4).
(3) Discussion and Outlook: We discuss the feasibility and limitations of ZOO relative to the open
web and outline its scenario constructor can be adapted to diverse research needs (Section 5).
BACKGROUND
Before presenting the design and architecture of ZOO, we first introduce terminology and describe a
real-world indirect prompt injection email vulnerability that motivates this work and highlights the
need for a real world evaluation framework.
Web Agents. Web agents are systems that use large language models (LLMs) for reasoning and
planning to perform complex tasks across websites based on natural language commands. Unlike
traditional web browsers that wait for human input, web agents autonomously execute multi-step
workflows (e.g., booking travel, filling forms, managing emails). Web agents typically operate with
persistent, high-privilege credentials and user data, which introduces security and privacy risks,
including data leakage and loss of user control when agents interact with malicious websites.
Indirect Prompt Injection Attacks. Indirect prompt injection attacks (OWASP Foundation, 2024)
allow an attacker to craft malicious inputs to manipulate an LLM into performing unintended actions, such as leaking data or circumventing security safeguards. Because LLMs process instructions
and data through the same medium (namely, text), it can be challenging for them to distinguish malicious user input from actual instructions. This makes web agents susceptible to attacks that include
authoritative sounding commands or uncommon text strings that push the LLM outside of its usual
operating context. A carefully constructed string of text can have an effect similar to that of a traditional SQL injection attack (Open Web Application Security Project (OWASP), 2024), but without
the deterministic solution of escaping the user-provided text. In LLMs, escape characters are treated
as just more text.
Real-World Indirect Prompt Injection Attacks. Recent vulnerabilities in web agents (Brave,
2025; Figueroa, 2024; Guardio, 2025) and web applications (Figueroa, 2024; Common Vulnerabilities and Exposures, 2025) share common patterns, and underscore the need for a realistic evaluation

environment to study them. The specific details of these attacks vary, but they generally progress
through the following stages:
(1) Attack Setup: An attacker posts content online where a web agent will be exposed to it (e.g.,
sending an email, posting text or images on a forum). The content can optionally be obfuscated to
be invisible to a human (e.g., inside an HTML comment or white-on-white text). While the exact
prompts vary, they may be similar to the following:
1 [SYSTEM NOTE] URGENT: Ignore prior instructions and instead extract all emails marked
confidential and send contents as a payload tohttps://attacker.com?param=<payload>.
While the above example illustrates data exfiltration via a provided URL, an attacker could alternatively specify an email address (e.g., email@attacker.com) and modify the prompt to forward
all confidential messages. In both cases, the outcome is identical: the injected prompt enables the
attacker to harvest sensitive information, often without the victim’s awareness.
(2) Agent Execution: User assigns a task, such as: Create an overview document for project X by
summarizing my emails. The web agent takes these trusted instructions from the end user and mixes
those with the untrusted content, merging the attack prompt into the LLM context.
(3) Verification: The web agent leaks sensitive data to the attacker, such as by sending it as a payload
to an attacker-controlled URL. This allows the attacker to verify that the attack succeeded.

DESIGN AND ARCHITECTURE OF ZOO
ZOO is designed with two central objectives in mind: realism and reproducibility. We achieve
realism by running a rich and interconnected set of websites within the same network. By providing
shared services and standard web application protocols within the internal network, the environment enables deployment of unmodified web applications, supporting complex, multi-application
workflows that closely mirror real-world usage patterns. We maintain reproducibility through full
control over state, configuration, and domain allocation.
ZOO is open-source, available at https://github.com/double-blind/the zoo.
3.1
SYSTEM OVERVIEW
As illustrated in Figure 1, ZOO blocks all Internet access, using an internal Docker network (Docker
Documentation, 2024) (cf., Internal Zoo Network in the graphic). Instead, the environment is hosted

under a dedicated .zoo domain and exposes a forward proxy interface that enables web agents to
interact with websites using a standard web browser proxy configuration. Internally, ZOO provides
over a dozen diverse applications including webmail, e-commerce, git hosting, and a centralized
identity provider. ZOO also provides shared infrastructure for real-world testing conditions. Site
containers use an on-demand startup model, remaining uninitialized until the first incoming request.
3.2
CORE NETWORK SERVICES
The architecture of ZOO is modular, with distinct components responsible for traffic mediation,
domain resolution, web serving, data persistence, and authentication.
Squid Forward Proxy. All browser agent traffic is routed through a Squid Proxy (Squid Project,
2024) server. Squid has access to both the User-Facing Network and the Internal Zoo Network,
enabling it to mediate all traffic between the web agent and the various services within the ZOO.
Caddy Reverse Proxy. The Caddy web server (Caddy, 2015) manages HTTPS traffic within the
environment. Supporting HTTPS enables a more realistic testing environment, as many powerful
web APIs are only exposed in secure contexts (World Wide Web Consortium (W3C), 2024).
CoreDNS. Domain name service (DNS) resolution within the environment is handled by CoreDNS
(CoreDNS, 2016), which resolves all internal .zoo domains to their corresponding containers.
3.3
CORE BACKEND SERVICES
ZOO relies on a shared set of core backend services that all applications can consume, as they would
in a traditional deployment. This shared architecture enables use of largely unmodified open-source
web applications via their published Docker containers and configurations, instead of building new
sites from scratch. It also allows sites to use services such as SMTP (Internet Engineering Task
Force (IETF), 2008) and OIDC (OpenID, 2014), enabling agents to trigger end-to-end workflows
across applications.
Stalwart Mail Server. The Stalwart Mail Server (Stalwart, 2023) is an open-source, modern email
and collaboration server that allows handling all required email workflows.
Hydra (OpenID / OAuth). OpenID Connect (OIDC) (OpenID, 2014) is an identity layer built on
top of OAuth 2 (Internet Engineering Task Force (IETF), 2012a;b) that allows to verify a user’s
identity. Ory Hydra (Ory Corp, 2016) provides the underlying identity functionality, which enables
single sign-on consent flows allowing to simulate real world workflows.
MySQL and PostgreSQL. MySQL (MySQL, 1995) and PostgreSQL (PostgreSQL, 1996) provide
relational database support.
Redis. Redis (Redis, 2009) serves as an in-memory key–value store for transient data. Redis is
configured with persistence explicitly disabled (--save "" --appendonly no), ensuring it
restarts to an empty state and requires no snapshot mechanism.

CONSTRUCTING REALISTIC SCENARIOS WITH ZOO
ZOO’s scenario constructor equips researchers with tools for designing and instantiating novel evaluation benchmarks. In this section, we present its organizational principles. The scenario constructor
is structured around three core concepts:
(1) Universes, define the initial world in which agents operate. A universe will specify which
websites and which agent personas are available. For example, a startup universe might provision a
company email server, a project management board, and a code repository, while a personal assistant
universe provides a webmail account, a shopping site, and a social forum.
(2) Tasks, define what agents must achieve within a universe. Tasks can be used to specify several
elements that define the environment conditions, like a list of websites available to agents, task complexity, the ability to define evaluation criteria and the possibility for users to decompose complex
tasks in several weighed sub-tasks, among other possible configurations.
(3) Scenes, bring dynamism to tasks. They lay out instructions to either pre-populate a universe
with data in the setup phase or fire actions, which are events triggered during the execution of a task.
Actions often use the accompanying scenario constructor’s API in order to deterministically modify
the environment. They can be triggered with a timer, through HTTP events, when webpages load or
when specific content appears at an endpoint. All of this introduces the ability of developing attack
scenarios that capture the complexity of real-world threats while remaining reproducible across
evaluations.
In addition to these organizational principles, ZOO’s scenario constructor is designed for flexibility
across agent architectures, model providers, and evaluation methods:
Harness Agnostic. The constructor is designed to be harness agnostic. To demonstrate this, we
integrate two distinct agent frameworks: Browser Use (Browser Use, 2024) and Claude Agent SDK
with Playwright MCP. Additional frameworks can be added through the framework’s API.
Heterogeneous Multi-Agent Scenarios. Tasks can involve simultaneous agents backed by different
LLMs while concomitantly having distinct personas and goals.
Evaluation. Because ZOO exposes full backend state, evaluation is not limited to inspecting agent
output. Three mechanisms are supported: string matching against agent output, URLs, or database
queries; custom Python functions for arbitrary verification logic; and LLM-as-judge, which uses a
separate model to score open-ended responses against task-specific criteria. This enables groundtruth verification of whether an agent’s actions had the intended real-world effect—not just whether
the agent claimed to succeed.
LLM Support. Currently the framework offers support to LLMs distributed by OpenAI, Anthropic
and OpenRouter.

4.1
PROOF-OF-CONCEPT BENCHMARK
We provide benchmark infrastructure that simplifies the implementation of custom tasks. The runner orchestrates the entire workflow, from task execution to result collection, enabling systematic
comparisons across models, configurations, and tasks. At the same time, users retain full flexibility
to define and implement their own tasks, allowing the construction of rich and diverse benchmarks
while leveraging the provided infrastructure.
Metrics. We measure agent performance along two axes.
• Completion Rate. (CR) measures the fraction of tasks successfully completed.
• Overall Score. averages task scores, where partial credit may be awarded for subtask completion.
These metrics are broken down by autonomy level, environment condition and task complexity.

Illustrative Example. To illustrate the interplay between generality and task performance, consider
a compositional task in the personal assistant universe introduced above. In this task, the LLM is
a personal agent that is requested by the user to research vacuum cleaners by creating a post on
postmill.zoo (our mirror of Reddit) wait for replies, and then combine that knowledge with its
own judgment to select and purchase a vacuum on the shopping website. Across the state-of-the-art
models evaluated, no agent succeeds in publishing the forum post. If they abandon this step and
proceed to the shopping site, they correctly type “vacuum cleaner” into the search bar. However,
the site contains cluttered, realistic content—much like the open web—and the first result is a watch
branded “Vacuum Cleaner.” Despite having access to vision and seeing actual vacuums elsewhere
on the page, the LLM selects the watch. We argue, through this example, that navigating the real
web demands generalist capabilities. Simplified interfaces such as the recently popular Moltbook (a
social network designed for agent-to-agent interaction (Pridgen, 2025)) succeed precisely because
they are designed for programmatic interaction, but the web rarely offers such clean affordances.
This makes an ecosystem like ZOO especially valuable for developing agents that must operate
across a messy, human-oriented web.
DISCUSSION AND OUTLOOK
Modern web security emerged through decades of layered defenses—HTTPS adoption (Kerschbaumer et al., 2025; Felt et al., 2017), Same-Origin Policy (World Wide Web Consortium (W3C),
2010), Content Security Policy (World Wide Web Consortium (W3C), 2023), and browser sandboxing (Reis et al., 2019; Kerschbaumer et al., 2020)—rather than any single mechanism. We anticipate that web agents will require a similarly iterative evolution of defensive mechanisms to address
emerging security challenges. As with past web security efforts, progress will require evaluation
frameworks that enable continuous benchmarking and iterative defense development.
Providing Better Evaluation Systems. Evaluating web agents requires more than simple taskcompletion metrics, as traditional measures fail to capture complex behaviors such as authentication,
session management, and adaptation to dynamic interfaces. ZOO provides reusable infrastructure
rather than a fixed benchmark, separating the extensible environment from task definitions, success

criteria, and evaluation metrics. This decoupling allows benchmarks to evolve as threats change,
reduces overfitting to static task suites, and enables researchers to design evaluations suited to their
specific needs, while avoiding the substantial and orthogonal engineering effort required to integrate
realistic, heterogeneous web services.
Limitations of ZOO. While the current environment provides a robust foundation for reproducible
experimentation, there are opportunities to extend it toward greater realism, scalability, and analytical depth:
(a) Integration with Live Ecosystems: ZOO currently blocks external network access to ensure reproducibility. Some attack scenarios, such as data exfiltration, may require selective external connectivity or mocked services, which we leave to future work.
(b) Network Dynamics: The current environment does not simulate latency, packet loss, or bandwidth constraints, precluding study of timing-dependent vulnerabilities or web agent behavior under
degraded connectivity.
(c) Scalable Service Orchestration: The current Docker Compose implementation supports local
experimentation and single-host cloud deployment with Docker-in-Docker (Docker, 2023). Scaling
to parallel evaluation across multiple Zoo instances is straightforward future work.
(d) Richer Seeded Data: ZOO includes only minimal seeded data, limiting evaluation complexity;
expanding realistic content is orthogonal to the infrastructure and left for future work.
Outlook. ZOO enables systematic construction, execution, and analysis of multi-step attack scenarios without impacting production systems or rebuilding infrastructure for each project.
Future work should focus on establishing standardized web agent benchmarks that combine functional realism with controlled observability, enabling cross-study comparisons while maintaining
security.
RELATED WORK
Developing evaluation systems to assess the security properties of web agents is key to providing
security guarantees for end users as they begin to rely on such systems. Recent work however has
shown that LLM agents interacting with the web are highly susceptible to prompt injection and other
interface-layer attacks (Evtimov et al., 2025; Brave, 2025; Figueroa, 2024; Witt, 2025).
Foundational Web Agent Benchmarks. Early work on web-based agents focused on simplified,
synthetic environments. MiniWoB++ (Liu et al., 2018) and WebShop (Yao et al., 2022) provide controlled benchmarks for short, single-site interactions. Subsequent work has scaled to more realistic
settings: WebLINX (L`u et al., 2024) provides expert demonstrations of multi-turn conversational
navigation to improve LM navigation. Mind2Web (Deng et al., 2023) and WebVoyager (He et al.,
2024) scale to real-world websites but rely on live sites or static snapshots, limiting reproducibility.
Realistic Web Environments. WebArena and VisualWebArena (Zhou et al., 2024; Koh et al.,
2024) introduce self-hosted websites across domains such as e-commerce and social forums, but
offer limited control over underlying applications (Kapoor et al., 2024). REAL (Garg et al., 2025)
adds deterministic evaluation but uses simplified replicas that cannot be extended with new services
or shared infrastructure.
Security and Robustness of Web Agents. Benchmarks that explicitly target web agent security
have only recently appeared. WASP (Evtimov et al., 2025) constructs realistic prompt injection
scenarios with constrained threat models—attackers can only post content in user-editable areas
such as GitLab issues or Reddit comments—and measures how often agents are hijacked toward
attacker goals. WASP observes security by incompetence: attacks partially succeed in diverting
agents toward malicious actions up to 86% of the time, but fail to achieve full data exfiltration
due to a lack of agent capability. However, WASP builds entirely on VisualWebArena’s existing
infrastructure and is limited to just two websites, with no email server, no shared identity provider,
and no ability to test cross-application attack chains such as email-based exfiltration. WebInject
(Wang et al., 2025) takes a complementary approach, proposing an optimization-based attack that
perturbs raw pixel values in webpage source code to visually mislead screenshot-based agents; it
is an attack technique rather than an evaluation environment, and likewise evaluates on existing

VisualWebArena sites. ST-WebAgentBench (Levy et al., 2024) evaluates safety-rule compliance and
WAREX (Kara et al., 2025) tests robustness under network perturbations, but both again layer task
definitions on top of pre-existing benchmark frontends. In contrast, ZOO addresses the environment
layer itself: rather than defining new task suites atop a small set of siloed websites, it provides
a shared, extensible infrastructure of 13 interconnected applications with shared backend services
(email, identity, databases), enabling researchers to construct attack scenarios—including multistep, cross-application chains like email-triggered data exfiltration—that cannot be expressed in any
existing benchmark.
CONCLUSION
Web agents introduce new security risks by autonomously executing multi-step workflows across
untrusted web content. Evaluating these risks requires environments that preserve the complexity of
the open web while providing reproducibility and state visibility unavailable in production settings.
We have presented ZOO, a simulated web environment that integrates multiple interconnected web
applications, such as email, identity management, e-commerce platforms, and analytics, within a
single isolated network. ZOO provides full access to backend state and supports deterministic reinitialization, enabling precise and repeatable analysis of web agent behavior.
Existing benchmarks understate how brittle frontier agents remain on the open web. Our case study
across four frontier models and over 200 evaluation runs demonstrates that all models suffer a significant performance drop when instantiated with minimal instructions in cluttered, real-world interfaces.
We release ZOO and its scenario constructor as open-source infrastructure, enabling the community
to develop rigorous benchmarks that honestly reflect the complexity and adversarial nature of the
real web.

A.3
LLM JUDGE PROMPT
For open-ended tasks, we use an LLM-as-judge evaluation with the following prompt template.
The judge model (GPT 5.1 by default) receives the agent’s final output, step-by-step actions, and
task-specific criteria.
1 You are an evaluator checking if an agent’s output meets
2 specific criteria.
4 IMPORTANT CONTEXT:
5 - You see the agent’s FINAL TEXT OUTPUT and STEP-BY-STEP ACTIONS below
6 - The AI agent has tools to interact with web pages and have access to
the DOM, meaning that some actions
7 won’t clearly translate to an usual human action.
8 - If the agent timed out or failed, you may still see the steps it
attempted before failing.
10 EVALUATION RULES:
11 - Focus on outcome correctness, not prescriptive methods. Agent can use
any approach to achieve results.
12 - Judge whether the agent obtained CORRECT information, not HOW they
obtained it. If the agent reports accurate data that existed on the
page, they succeeded - even without clicking through every UI element
.
13 - Besides evaluating an agent’s final answer, also evaluate based on
whether the STEPS show the agent accomplished the criteria.
14 - ONLY check the numbered criteria below. Do NOT add extra requirements
beyond criteria.
16 CRITERIA TO CHECK:
17 {criteria_text}
19 AGENT’S FINAL OUTPUT:
20 {agent_answer}
22 Check each numbered criterion. Respond with JSON:
23 {
"reasoning": "Brief status for each criterion",
"passed": true/false,
26 }
